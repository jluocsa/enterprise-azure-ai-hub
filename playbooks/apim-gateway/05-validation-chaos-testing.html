Why It Matters

Unverified failover policies frequently fail in production due to missing RBAC roles on the secondary PAYG resource, buffered SSE streams, or snapshot version mismatches.

Key Takeaway

Execute the 4-step fault-injection protocol in staging and require all 12 G1–G12 gateway controls before routing production traffic.

Practical Application

Run Steps 1–4 during Week 2/3 staging sign-off and paste G1–G12 into the gateway infrastructure pull request.

0. Offline Policy XML Preflight ​

APIM policy expressions use C# inside XML attributes or element text (Microsoft Learn policy expression syntax) [M]. Encode embedded attribute quotes as &quot; and C# generic brackets as &lt; / &gt;; XML parsing restores the original expression.

Run npm run verify before staging: its check:apim gate parses both the downloadable policy and the built Studio's default copyable XML, rejecting malformed expressions, missing artifacts, missing rendered policy output, and violations of the static per-attempt spillover body contract [Arch].

For G8, the same gate requires every visible backend forward-request to set literal buffer-response="false". Microsoft Learn documents that this attribute defaults to true and recommends false for immediate SSE chunk forwarding; its SSE guidance also warns against response-buffering policies, body logging, and response caching [M]. The local regression guard rejects outbound set-body, validate-content, json-to-xml, xml-to-json, find-and-replace, xsl-transform, and cache-store, including nested branches, plus direct context.Response.Body access in outbound expression text or attributes. Header/status access and inbound PTU request-body rewriting remain allowed [Arch].

These are static checks, not APIM policy schema validation, C# compilation, or a complete streaming proof. They do not resolve inherited <base />/policy fragments, C# aliases or indirect body access, diagnostic body logging, or alternate Studio settings (including deliberately disabling SSE). Review the effective policy and diagnostics, then run the staging probes below; offline success does not establish the TTFT target or safe mid-stream retry behavior [Validate].

1. Four-Step Staging Fault-Injection Protocol [Validate] ​

  1. Step 1 — Synthetic 429 Retry-After Trip Test: Temporarily route Priority-1 to a mock APIM endpoint (or minimal 15-PTU canary deployment under synthetic burst) returning HTTP 429 with Retry-After: 25. Verify:
    • Call #1 transparently retries inside <backend> onto Priority-2 Standard PAYG and returns HTTP 200 (x-gateway-routed-sku: standard-spillover).
    • Calls #2..N during the next 25s route directly to Priority-2 in <5ms gateway overhead without hitting Priority-1.
    • After 25s, traffic automatically heals back to Priority-1 PTU-M.
  2. Step 2 — Unbuffered SSE TTFT Parity Probe: Send a 4,000-token stream: true request through APIM and directly to the VNet Foundry endpoint. Confirm gateway TTFT overhead is <35ms (if TTFT jumps to full completion time, an outbound body-inspection policy is buffering the stream).
  3. Step 3 — SKU Breakpoint Compatibility Check: Send a payload containing prompt_cache_breakpoint and prompt_cache_options through a GPT-5.6 PTU-M route; confirm HTTP 200 and non-zero cached_tokens on Pass 2.
  4. Step 4 — FinOps Header & Cache-Key Isolation Probe: Send 10 sequential calls with distinct x-cost-center values (CC-1001..CC-1010) but the same sharded prompt_cache_key. Confirm Pass 2–10 hit the prefix cache (≥80% hit rate) while all 10 CostCenter values appear in App Insights metrics.
