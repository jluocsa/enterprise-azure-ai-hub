04 · Deployment SKU Boundary & PTU Capacity Math ​

1 · Start2 · Qualify & Size3 · Design4 · Validate5 · Govern
4 min readVerified 2026-11-25 13:40 PST
Why It Matters

Sizing PTU reservations using legacy GPT-4o formulas—or assuming GPT-5.6 PTU-M supports breakpoints—leads to 2.56× capacity shortfalls or HTTP 400 errors.

Key Takeaway

GPT-5.6 deducts cached tokens 100% from PTU draw (no breakpoints on PTU-M), while GPT-6/6.1 support PTU-M breakpoints with 0.1x/0.05x read and 1.25x write weights.

Practical Application

Select a workload preset in the interactive calculator below, adjust RPM and token parameters, and copy the PTU + shard estimate.

Enterprise production workloads commonly pair Provisioned Throughput (PTU-M) base capacity with Standard (Pay-As-You-Go) spillover. Available caching parameters and PTU utilization formulas differ sharply between GPT-5.6 and GPT-6 / GPT-6.1 [M].

3. Two-Regime PTU Sizing Math & Worked Example ​

  • Regime 1 — Pre-GPT-6 (including GPT-5.6):
    • Normalized TPM = Input TPM × (1 − Cache Rate) + (6 × Output TPM)
    • Raw PTUs = Normalized TPM ÷ Input TPM per PTU → round up to the 5-PTU scale increment
    • At 100 RPM, 10,000 input tokens, and 500 output tokens on gpt-5.6-terra (3,000 Input TPM/PTU):
      • 80% cache hit rate: 500,000 Normalized TPM → 166.7 raw → 170 PTUs (at the 5-PTU increment).
      • 0% cache hit rate: 1,300,000 Normalized TPM → 433.3 raw → 435 PTUs (2.56× deployed PTU spike; 2.60× raw TPM).
  • Regime 2 — GPT-6 & GPT-6.1 Normalized Tokens (<=272K):
    • Normalized TPM = (Uncached × 1.0) + (Cached Read × w_read) + (Cache Write × 1.25) + (Output × 5.0)
    • Where w_read = 0.10 on GPT-6 and 0.05 on gpt-6.1-sol. Size base PTUs so steady peak demand stays below queuing saturation (~60–70% utilization).

4. Live PTU & Cache-Shard Estimator ​

The calculator blocks results and Markdown export for blank, non-finite, out-of-range, or arithmetic-overflow inputs instead of silently clamping them. Its 100–272,000 input-token range is the local short-context estimator boundary, not a model context limit; inputs above it require a long-context sizing model. Other accepted ranges are shown on the controls, and read/write validation applies only to GPT-6/6.1. Field-linked errors clear when valid inputs or a preset are restored. These offline UI checks do not certify regional capacity, quota, or measured throughput [Arch].

Azure prompt caching requires a request of at least 1,024 tokens with an identical initial 1,024-token prefix (Microsoft Learn) [M]. For this single-profile estimator, modeled input below that boundary must use 0% cached input share; positive shares hide estimates and block Markdown export with errors linked to both controls rather than silently granting cache savings. At 1,024 tokens, positive shares are accepted as assumptions, not proof of a reusable prefix or measured hits. Mixed-length traffic can have cache-eligible requests even when its average is below 1,024: size eligible and ineligible cohorts separately instead of applying this conservative local check as a service rule for averages. Offline regressions cover all supported models, fractional values below the boundary, zero-share sizing, exact-boundary recovery, and preset recovery [Arch].

Finite values alone do not ensure reliable integer estimates. The calculator also requires the conservative arithmetic budget RPM × (1.25 × input tokens + 6 × output tokens) × surge × 12 to stay within JavaScript's Number.MAX_SAFE_INTEGER. This upper envelope covers both model regimes and annual seasonal arithmetic before rounding PTU, token, and shard counts; it is a local numerical-safety policy, not an Azure capacity limit. Oversized inputs hide estimates and block even direct copy-handler invocation with field-linked errors. Reduce RPM, output tokens, or surge rather than accepting imprecise counts; ordinary fractional workload averages remain supported. Offline regressions cover every selectable model, combined-workload overflow of this budget, and recovery to valid inputs and presets [Arch].
